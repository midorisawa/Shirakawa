# Ollama（ローカル）で使う

接続先に「Ollama（ローカル）」を選ぶと、投稿の判定をお使いのPC上のOllamaで行えます。APIキーは不要で、投稿本文と判定条件はPCの外へ送信されません。ChromeとEdgeのどちらでも同じ手順で使えます。

## 用意するもの

- [Ollama](https://ollama.com/)（0.35以降。判定に使う `/v1/systemone` に対応したバージョンです）
- 判定モデル `nimble`（約9.5GB。判定中はこの分のメモリを使います。他のモデルは「使えるモデルと精度」を参照）

## 手順

### 1. Ollamaとモデルを用意する

Ollamaをインストールして起動し、ターミナルで次を実行します。

```sh
ollama pull nimble
```

### 2. OllamaがShirakawaからの接続を受け付けるようにする

Ollamaは、許可されていない拡張機能からの接続を拒否します。環境変数 `OLLAMA_ORIGINS` に、Chrome Web Store版のShirakawaを許可する次の値を設定して、Ollamaを再起動してください。

```
OLLAMA_ORIGINS=chrome-extension://gnlkgpphbjmbfpgbicaebhlmacnnhmmf
```

- ZIPから読み込んだ場合やEdgeでは、拡張機能のIDが異なることがあります。Chromeは `chrome://extensions`、Edgeは `edge://extensions` で「デベロッパーモード」を有効にすると、Shirakawaの欄にIDが表示されます。そのIDを `chrome-extension://<拡張機能ID>` の形で指定してください。
- OSごとの環境変数の設定方法は、[Ollama公式のFAQ](https://github.com/ollama/ollama/blob/main/docs/faq.md)をご確認ください。

macOSでOllama.appを使っている場合の例（手元ではこの方法だけを確認しています）:

```sh
launchctl setenv OLLAMA_ORIGINS "chrome-extension://gnlkgpphbjmbfpgbicaebhlmacnnhmmf"
```

実行後、メニューバーのOllamaのアイコンから終了し、Ollamaを起動し直します。この設定はPCを再起動すると消えます。残したい場合は、ログイン時に実行する仕組み（LaunchAgentなど）に入れてください。

### 3. Shirakawaで接続先を選ぶ

1. 拡張機能の設定画面を開き、「API接続」タブの接続先で「Ollama（ローカル）」を選びます。モデルIDは `nimble` になります。
2. 「接続を確認する」を押します。`localhost:11434` への接続許可を求められるので、許可してください。
3. 「接続できました」と表示されれば完了です。
4. 設定画面上部のスイッチを「有効」にして保存します。x.comを開き直すと、判定が始まります。条件に当てはまる投稿は、「非表示条件「…」0.xx」のプレースホルダーに置き換わります。

## うまくいかないとき

| 表示 | 原因と対処 |
|---|---|
| Ollamaが接続を拒否しました（OLLAMA_ORIGINSに…） | 手順2の設定が反映されていません。表示されたIDを `OLLAMA_ORIGINS` に設定し、Ollamaを再起動してください。 |
| Ollamaに接続できません | Ollamaが起動していないか、`localhost:11434` への接続が許可されていません。起動を確認し、「接続を確認する」をもう一度押してください。 |
| localhost:11434への接続が許可されていません | 許可ダイアログで拒否しています。もう一度「接続を確認する」を押して許可してください。 |
| モデルが見つかりません | 設定したモデルIDを `ollama pull` で導入してください（例：`ollama pull nimble`）。 |
| 判定が始まらない | 設定画面のスイッチが「無効」のままか、x.comのタブが古いままです。有効にして、x.comをリロードしてください。Ollamaのログ（`~/.ollama/logs/server.log` など）に `POST /v1/systemone` が出ていなければ、判定がOllamaに届いていません（ログにスコアは出ません）。 |
| 判定が遅い | 下の「実測」を参照してください。他のモデルが生成中だと、完了を待ってからnimbleがロードされます。 |

## 動作の仕様

- 既定のモデルIDは `nimble` です。
- 使用額上限と利用量の記録は適用しません。
- 判定リクエストのタイムアウトは120秒です（他の接続先は30秒）。他のモデルが生成中だと、Ollamaは完了を待ってからnimbleをロードするためです。
- 拡張機能からOllamaへの並列リクエスト数は1です（他の接続先は2）。拡張機能は画面に見えている投稿を優先して判定しますが、Ollamaは並列に送っても直列にしか処理せず、待ち行列も届いた順なので、並列で送るほど1件あたりの待ち時間が延び、いま見ている投稿が画面外の投稿の判定に待たされるためです。
- 判定に失敗した投稿は、既定では表示されます。自動では再判定されません。

## 使えるモデルと精度

Ollama 0.35 の判定モデルとして、`nimble`（9B）のほかに、実験的な `tev1`（4B）と `tev1:0.8b`（0.8B）が公開されています。設定画面のモデルIDを変えると使えます。

3つとも、手元で接続確認と判定が動くことを確認しました。ただし、軽いモデルほど精度は下がるため、`nimble` をおすすめします。既定のブラックリストの有効なルール8件を使い、攻撃的な投稿3件と普通の投稿3件を判定した、小規模な確認です（ベンチマークではありません）。表は、ルールごとのスコアの最大値です（既定の閾値は0.9）。

| モデル | 容量 | 1件あたり | 攻撃的な3件 | 普通の3件 |
|---|---|---|---|---|
| `nimble` | 9.5GB | 約1.5秒 | 0.77 / 1.00 / 0.86 | 0.00 / 0.01 / 0.01 |
| `tev1` | 4.5GB | 約1.0秒 | 0.45 / 0.82 / 0.86 | 0.00 / 0.02 / 0.02 |
| `tev1:0.8b` | 811MB | 約0.3秒 | 0.49 / 0.37 / 0.73 | 0.16 / 0.55 / 0.67 |

- `tev1` は、攻撃的な投稿のスコアが `nimble` より低く、閾値0.9では見逃しが増えます。
- `tev1:0.8b` は、攻撃的な投稿が低く、普通の投稿に0.5を超えるスコアが出ることがあり、閾値で分けにくくなります。

## 実測

環境: macOS、Ollama 0.35.0、nimble（9B、Q8_0、100% GPU）、`OLLAMA_NUM_PARALLEL=1`、`OLLAMA_MAX_LOADED_MODELS=1`、`OLLAMA_KEEP_ALIVE=120`。計測日は 2026-10-02 です。計測中に別のリクエストが同じ Ollama に入ると、所要時間が大きく変わるため（実際に最大2倍超になりました）、ブラウザの拡張機能を止めて計測しています。

### 並列リクエスト数 4 → 2 → 1（`scripts/bench-ollama-queue.mjs`）

画面外の投稿12件（優先度2）を送った直後に、画面内の投稿3件（優先度0）を送ります。実際の `src/background.js` と実際の Ollama を使い、判定条件は既定の有効ルール8件です。3回計測した中央値です。

| 指標 | 並列4件 | 並列2件 | 並列1件 |
|---|---|---|---|
| 画面内3件がすべて判定されるまで | 10.5 秒 | 7.5 秒 | 6.0 秒 |
| 全15件が判定されるまで | 22.7 秒 | 22.7 秒 | 23.0 秒 |

- 各回の値: 画面内は並列4件 `[10.6, 10.5, 10.5]`、並列2件 `[7.5, 7.4, 7.5]`、並列1件 `[6.0, 6.1, 6.0]` 秒でした。
- 画面内の判定は、並列数が少ないほど速くなります。画面外の投稿が Ollama の待ち行列に先に入らず、拡張機能側の優先度制御が効くためです。
- 全体の所要時間は変わりません。Ollama は直列に処理するので、総処理量が同じだからです。

再計測: `CONCURRENCY=1 node scripts/bench-ollama-queue.mjs`（`CONCURRENCY`、`PORT`、`TRIALS`、`BACKLOG`、`VIEWPORT` 環境変数で並列数、Ollama のポート、回数、件数を変更できます）。

### `OLLAMA_NUM_PARALLEL` を 1 から 4 にした場合

別ポートの使い捨てサーバーで、12件を並列に送りました（判定条件8件、3回計測）。

| `NUM_PARALLEL` | 12件の所要時間（3回） | nimble のメモリ |
|---|---|---|
| 1 | 16.0 / 16.2 / 16.0 秒 | 9.9GB |
| 4 | 16.0 / 16.1 / 16.0 秒 | 9.9GB |

所要時間は変わりませんでした。出力が3トークン程度で、時間の大半は入力の処理（計算量で決まる）にあるため、並列化しても速くならないと考えられます。`NUM_PARALLEL` は全モデルに効き、KV キャッシュがスロット数分だけ確保されるので、qwen などの大きなモデルのメモリが増えます。効果がないので、上げないままにしています。

### モデルのロードと入れ替え

| 状況 | 所要時間 |
|---|---|
| nimble がアンロード済み（コールドロード） | 1.5 秒 |
| ロード済み | 0.05 秒 |
| gpt-oss:20b がアイドルでロード中から入れ替え | 1.6 秒 |
| gpt-oss:20b が約17秒の生成中に nimble を要求 | 15.5 秒待って成功 |
